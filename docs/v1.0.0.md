# StrixOps v1.0.0

Release date: 2026-09-09.

Detailed setup and usage: [English README](../README.md) · [简体中文](../README.zh-CN.md).

The first complete StrixOps release integrates the existing Python scan engine,
FastAPI API, and web Console. It includes all built-in runtime system prompts
and skills. The `strix` and `strixops` CLI commands use the same native engine;
an external Strix checkout or Python runtime is not required.

## Installation

Requirements: Python 3.12 or newer, Docker with the configured sandbox image,
and a compatible model provider. The wheel includes the built web Console;
Node.js is needed when building the frontend from source.

To install a release wheel:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install ./strixops-1.0.0-py3-none-any.whl
.venv/bin/strixops-console --runs-root "$PWD/strix_runs"
```

To run from the source checkout:

```bash
npm --prefix console/web ci
npm --prefix console/web run build
uv sync --frozen --no-dev
bash containers/build-images.sh
uv run --no-dev strixops-console --runs-root "$PWD/strix_runs"
```

Build the sandbox once before launching scans, or use an already installed
compatible image. The default is `strixops-sandbox:1.3.0`, extending
`ghcr.io/usestrix/strix-sandbox:1.3.0`; Docker image and provider dependencies
still apply.

Open `http://127.0.0.1:8300`, configure a model profile in Settings, and create
a task. One process serves the API and frontend. Subsequent starts only need
the Console command; rebuild the frontend after changing its source. Existing
Console configuration and run directories remain usable.

## Included features

| Area | Behavior |
|---|---|
| Integrated Console | Web and internal scans, model profiles, projects, operator hints, live conversations, agents, findings, reports, and evidence export |
| Optional multi-target tasks | Separate launch-page button, per-line validation, UTF-8 text import, and preserved single-target drafts; all targets share one native run |
| Complete scope handling | Repeated CLI targets and list files; full target scope carried through agents, reruns, project checks, search, and report aggregation |
| Expandable skill list | Project overview starts with five entries and can expand to the full recorded list, with hit and task counts |
| Prompt diagnostics | Saved model-route selection, required test task, per-file progress and cancellation, refusal classification, and original model replies |
| Prompt and skill consistency | Bundled runtime assets, run-owned snapshots, hashes, and per-agent prompts; Console edits affect subsequent runs |
| Agent delegation | Baseline child guidance, shared scope, bounded depth and concurrency, and descendant completion checks |
| Assessment state | Coverage, threat models, authors, and revisions shared across agents and persisted with the run |
| Findings and reports | Dynamic and dependency findings, source and fix details, revision history, project aggregation, and model-assisted final composition with a deterministic fallback |
| Evidence and completion | Agent shutdown and sandbox writer stop before capture; persisted attachments, binary downloads, ZIP export, and verified cleanup before success |

Multi-target tasks accept 2–100 distinct targets in the Console. The original
single-target form remains the default. Console imports accept UTF-8 `.txt`
files up to 512 KiB; CLI list files accept up to 1 MiB each. Blank lines and
full-line comments are ignored, and exact duplicates are merged. One scan type,
model route, and instruction set apply to the entire task.

The Skills-page diagnostic sends the selected saved file unchanged as system
instructions and the entered task as the user message. It does not execute
scan tools or assemble the full scan context. Results distinguish no detected
refusal, structured refusal, explicit policy blocking, provider errors, and
inconclusive replies. Review the response to assess task completion. Starting
checks uses the selected provider's normal model quota.

Evidence references support delivered directories and filenames adjacent to
Chinese punctuation. Cleanup errors identify delivery counts and unresolved
references. Run workspaces remain available for recovery when finalization
fails; missing evidence is not counted as delivered.

## Operational limits

- Coverage is agent-reported. Completion or no findings does not establish
  exhaustive testing. Legacy runs without assessment records show unknown data.
- Recorded skill counts include dynamic load events and explicit agent-injection
  events. They do not enumerate every automatic preload or measure skill quality.
- Agent limits default to depth 2, 4 active agents, and 12 lifetime agents,
  including the root. These limits are not a token or monetary budget.
- Model behavior depends on the route, target, access, and instructions. This
  release does not claim measured detection rates or complete upstream parity.
- The Console remains a single-user application. Tenant isolation, account
  management, billing, and an authentication boundary are outside this release.
- Forced process termination, host failure, or Docker failure can require
  recovery from retained workspace and container state.

## Published contents and development verification

The published repository and distribution packages retain the complete runtime
prompt and skill library. Local credentials, scan outputs, caches, external
design/development instructions, test suites, and scripted test fixtures are
excluded.

Development regression suites and detailed verification records are provided
only in the local internal test workspace.
