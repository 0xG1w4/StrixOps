# StrixOps v1.1.8

Release date: 2026-09-11.

The task page now has five main tabs: **Conversation, Findings, Notes, Files,
Report**. Agent selection and operator hints share the Conversation view, and
evidence and other saved artifacts use one file browser.

## Task page

- Conversation combines the Agent hierarchy, the selected Agent's timeline and
  a hint composer at the bottom. The recipient follows the selected Agent;
  the all-Agents timeline explicitly addresses the root Agent.
- Drafts are kept separately by task and recipient while using the Console.
  Sending fixes the recipient and text, so switching views cannot redirect an
  in-flight hint or clear another Agent's draft.
- Notes contains shared notes, test coverage and threat models. Their existing
  records and distinct meanings are preserved.
- Files combines evidence and other artifacts by their full run-relative paths.
  Evidence metadata and unavailable deliveries remain visible alongside shared
  preview, search and download controls.
- Findings and Report retain their separate purposes: individual discoveries
  and the complete assessment narrative.

Saved links to the former Agents/Hints tabs open Conversation. Assessment links
open Notes with test coverage selected; Evidence links open Files filtered to
evidence, and Artifacts links open Files. Selected Agent and notebook view can
be retained in the task URL.

## Hint delivery

Explicit recipients are now strict. A missing or inactive Agent does not cause
the hint to be silently redirected to root. New submissions check both task
and Agent availability; delivery checks again because an Agent can finish after
a hint is queued. Failed deliveries have a persisted, visible failure state.

An accepted new hint is queued; delivery means accepted into the Agent's mailbox,
and acknowledgment means the Agent echoed the hint token. Acknowledgment does
not establish that the requested work is complete. Hints retain the existing
stream interruption and continuation in the Agent's task context.

The composer supplies a request ID when submitting. Retrying an uncertain
submission with the same ID and unchanged payload retrieves the existing result
instead of creating a duplicate. This check can recover an existing submission
after a task has finished; it does not permit a new hint to a finished task.
Older callers without a request ID keep the existing API entry point, and an
omitted recipient keeps the root-Agent default. Older saved hint history remains
readable.

The change does not modify model routing, scan tools, containers or the separate
MCP task flow. See [the task page guide](task-page.md) for interaction details.

## Upgrade

```bash
git fetch origin tag v1.1.8
git switch --detach refs/tags/v1.1.8
npm --prefix console/web ci
npm --prefix console/web run build
uv sync --frozen --no-dev
```

Restart Console with the existing persistent paths after current work completes.
New engine processes use the stricter hint delivery behavior; already-running
engines retain the version they started with. No task-data migration, sandbox
image rebuild or certificate reimport is required.

## 中文重點

- 任務主標籤整理為「對話、發現、筆記、檔案、報告」。
- 對話整合代理選擇與底部 hint 輸入，草稿依任務及代理分開保留。
- 「筆記」可切換共享筆記、測試覆蓋、威脅模型。
- 證據與其他產物共用檔案檢視，保留收集資訊與未交付狀態。
- 指定代理拒收時明確顯示失敗；不再悄悄改送主代理。
- 不確定是否送出時使用原請求 ID 確認結果，避免重複指令。
- 舊頁面連結仍可開啟；更新並重新啟動的新任務採用新版投遞邏輯。
