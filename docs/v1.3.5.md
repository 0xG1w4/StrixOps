# StrixOps v1.3.5 stable baseline

Baseline date: 2026-09-17.

The maintained stable branch
**[`v1.3.5-release`](https://github.com/0xG1w4/StrixOps/tree/v1.3.5-release)**
starts from the scan engine, prompts and skills at
`85d980b1438ac868f8abac8baabed1c60263647f`. It also backports Console overview
selection, project filtering and bulk deletion from `93f503f`, including deletion
guards in the Console API and report service. It also includes transactional
settings/project storage, stale-editor conflict protection and startup model
context discovery. Targeted prompt changes include skill revisions and corrected
internal discovery tool references to `create_finding`; version metadata remains 1.3.5.
The `release` suffix is part of the branch name.

Use **`v1.3.5-release`** for maintained stable installations. The preserved
**`refs/tags/v1.3.5`** tag is a fixed historical snapshot at `427f293`, which
includes the original version metadata and documentation updates on top of the
baseline and predates this backport. The tag is unchanged and does not contain
overview selection, bulk deletion, the settings-storage fix or startup context discovery; pull
**`v1.3.5-release`** to obtain those updates. This branch update does not create
a formal GitHub Release.
**`main` and `v1.4.0-dev` are development versions** and may contain changes
outside this stable baseline.

## Included since v1.3.4

- **Service maintenance:** stop the owned Console, scan engines and containers
  without requiring idle saved state; check stale MCP captures during install
  using the project's Python environment and verified container identity.
- **Report generation:** retain drafts through finalization, distinguish drafts
  from final model reports, show failure diagnostics, and regenerate a saved
  task's report in the background. Model profiles can select a separate report
  model, API mode and reasoning effort.
- **Report sources:** combine vulnerability/internal findings, shared notes,
  coverage, threat models and structured credentials. General evidence-file
  bodies are excluded; explicitly structured credential CSV files remain an
  intentional exception.
- **Credentials:** Agents maintain explicit credential records and validation
  state. Bulk imports retain complete datasets, CSV export includes the available
  inventory, and reports use bounded samples. Narrative text is not treated as a
  credential record merely because it matches a pattern.
- **Task execution:** bounded recovery can resume eligible interrupted model
  streams from saved Agent sessions. Each task can select Default or Deep mode.
- **Task continuation:** rerunning offers a new task or a continuation seeded
  with the previous final model report, with optional additional instructions.
  Tasks without a final report can only start a new task through this flow.
- **Console and attachments:** improve conversation layout, use Simplified
  Chinese consistently in the UI, render recognizable Mermaid diagrams with
  mislabeled fences or line breaks, and prevent active attachments from executing
  as Console content.
- **Overview task management (stable backport):** select individual tasks, filter
  by project, select all eligible tasks across the current filtered result, and
  delete the confirmed selection with separate success and failure results.
- **Concurrent settings updates:** serialize complete read/modify/write operations
  across threads and processes, use unique private temporary files for atomic
  publication, and reject unreadable or invalid existing JSON instead of resetting
  it. Model-profile, integration, project and scope editors retain drafts and
  reject stale revisions; reload the editor before retrying a conflicting save.
  Older API clients may omit the revision precondition and retain their existing
  update semantics. No manual data migration or sandbox-image rebuild is needed.
- **Startup model context:** resolve the selected scan route's advertised capacity
  before starting its sandbox and agents. Save its source and compaction threshold
  with the task, and use that same capacity for root, children and their summaries.
  When metadata is missing, run a bounded startup probe. Show each agent's latest
  request input usage separately from cumulative billing tokens.

## Startup model context

Each live scan first makes a bounded, read-only request to its configured API's
`/models` endpoint. Only metadata for the exact selected model is accepted.
If metadata includes the capacity, no inference probe is needed.
An API that does not advertise context capacity falls back to the bundled model
catalog, then `STRIX_CONTEXT_FALLBACK_TOKENS` (default 200,000).

When API metadata does not provide a capacity, initialization also runs one
bounded probe sequence with synthetic text, using the selected API mode and
reasoning configuration. It does not repeat for individual agents or turns.
A provider error that explicitly declares the context limit can correct the
startup budget; a successful request only records an accepted input size, never
an inferred maximum. Successful probes require input usage and marker recall;
this can detect some truncation but cannot prove all input was retained. A rate
limit, timeout, body-size rejection or unrelated API error is not a context limit.

The task record distinguishes **API reported**, **API error reported**,
**model catalog reference** and **unconfirmed fallback** capacity, and retains
available probe results. An advertised value is not a stress-tested
guarantee of the serving route's actual limit. Model catalogs such as
[OpenRouter's model list](https://openrouter.ai/docs/api/api-reference/models/get-models)
can supply context metadata; compatible APIs that only return model IDs cannot.
The saved startup value does not change when a model profile is edited later.
Dry runs skip discovery and probing; older tasks show no recorded capacity.

Probes can incur input/output token charges; valid provider usage is included in
the run's cumulative token counters. Defaults bound them to four requests,
60 seconds overall, 20 seconds per request, 32,768 locally estimated input tokens
per request and 65,536 in total. The output budget is at most 64 tokens per request.
Configure these with `STRIX_CONTEXT_PROBE_MAX_REQUESTS`,
`STRIX_CONTEXT_PROBE_TIMEOUT_SECONDS`, `STRIX_CONTEXT_PROBE_REQUEST_TIMEOUT_SECONDS`,
`STRIX_CONTEXT_PROBE_MAX_INPUT_TOKENS` and `STRIX_CONTEXT_PROBE_TOTAL_INPUT_TOKENS`.
Set `STRIX_CONTEXT_PROBE_ENABLED=false` to disable paid probes while retaining
metadata discovery. A bounded probe may finish without discovering the maximum;
in that case the catalog or fallback capacity remains explicitly unconfirmed.

The conversation footer shows input/capacity tokens, a small progress bar and
percentage for the selected agent; the combined conversation view uses root.
Switching to a child changes all three to that child's own measurement. Input
counts stay unabridged; capacity uses compact K/M labels. Percentages use the
original capacity, and the tooltip preserves exact counts. Estimates and
reference capacities use `≈`; missing measurements show `—` without a progress
bar. Percentages above 100% remain visible while the bar stops at 100%. The
tooltip includes the agent name and provenance without a separate context panel.
Each main model request publishes a local estimate of its complete input before
sending. When the response reports input token usage, that value replaces the
estimate. The display describes the current/latest request's input, not a running
sum or a token-by-token measurement while generating. After compaction, the next
request replaces the prior measurement with the smaller input. Summary and other
auxiliary model calls do not overwrite the agent's main-context measurement.
Unknown measurements stay unrecorded, and requests for a different model do not
inherit the scan model's capacity. Raw requests, credentials and provider error
bodies are not stored in these diagnostics.

Existing input/output token counters remain cumulative across the run. Automatic
compaction still runs at execution-cycle boundaries; per-request measurements do
not introduce a per-request hard limit or guarantee lossless summaries. A
separately configured report model retains its independent budget lookup.

## Overview selection and bulk deletion

1. In the overview, narrow the task list by search, scan type or project. Project
   choices include all projects and tasks without a project.
2. Select individual rows or use **Select all** to include eligible tasks across
   every page of the current filtered result. Changing a filter clears the
   selection. Tasks that arrive after selecting all are not selected automatically;
   live tasks and tasks already cleaning up cannot be selected.
3. Open bulk deletion and review the confirmation's complete list of task names,
   targets and total count. The scope is fixed while confirmation is open.
   Confirming permanently deletes those tasks' saved reports, evidence and logs.
4. Check the result: successful deletions are counted separately, and each failed
   task is listed with its reason. Failures do not prevent the remaining confirmed
   tasks from being attempted. Failed tasks that remain eligible stay selected
   so they can be retried after the issue is resolved.

The API checks each task again before deleting it. An active owned engine,
running or finalizing task, in-progress cleanup, report generation, queued work
or unreleased queue resources prevents deletion. If queue activity or cleanup
cannot be verified, deletion is blocked. Report generation and deletion share
an exclusive guard so a report cannot start or publish into a task being removed.
Finish or stop the relevant work and let resource cleanup complete before
retrying; batch deletion does not stop active tasks automatically.

## Stable baseline scope

This branch starts from `85d980b` and selectively backports `93f503f` for overview
selection, project filters, bulk deletion and the associated Console deletion
guards, plus the Console settings-storage fix and startup context discovery
described above. Targeted prompt changes include skill revisions and corrected
internal discovery tool references to `create_finding`. The Web Default Standard
preload introduced in `a0e9779` has been withdrawn; Default keeps its previous
skill selection. Standard remains available for explicit loading. Internal and
Deep mode selection and runtime limits are unchanged.
The branch intentionally excludes:

- `b4ccb77`: the revised shared Web assessment workflow and related prompt changes.
- `3846003` and `65dc237`: later context-exhaustion and truncated-summary recovery.

Default/Deep selection and report-based continuation are included; the later
workflow rewrite is not. Existing model retries are bounded. Upstream API errors,
context limits, truncated output and report-generation failures can still occur.

## Fresh source installation

Use a supported Linux or macOS host with Python 3.12+, uv, Node.js 20.9+/npm and
Docker available. From a terminal:

```bash
git clone --branch v1.3.5-release https://github.com/0xG1w4/StrixOps.git
cd StrixOps
./strixops.sh install --build-images
./strixops.sh start
./strixops.sh status
```

Open <http://127.0.0.1:8300>. Follow the [account guide](authentication.md) and
configure a model profile before starting an assessment.

An archive downloaded from the stable branch contains source that still needs
to be built. After extracting it, enter the extracted
directory and run the same `install`, `start` and `status` commands. If the
required sandbox image already exists, use `./strixops.sh install` without
`--build-images`.

## Upgrade an existing source checkout

Save local edits, including prompt/skill changes, and back up the configured
state and run directories before changing deployments. Let work finish, or stop
it before switching versions. For a checkout managed by `strixops.sh`:

```bash
cd /path/to/StrixOps
./strixops.sh stop
git fetch origin
git switch v1.3.5-release
git pull --ff-only
./strixops.sh install
./strixops.sh start
./strixops.sh status
```

For systemd or another supervisor, stop/start the service through that manager.
Reload the browser after installation. If switching or the fast-forward update
fails because of local changes or divergent commits, save and reconcile them
before retrying. `git pull` on `main` updates development code. Switching source
versions does not undo data changes made by a newer development deployment.

The sandbox image remains **`strixops-sandbox:1.3.0`**; product and sandbox versions
are separate. This version does not require rebuilding an already compatible
sandbox image or reimporting the existing MCP proxy CA.

## Build and install a local wheel

Follow the [packaging instructions](../README.md#packaging) to build a wheel from
the stable branch. The resulting `dist/strixops-1.3.5-py3-none-any.whl` contains
the rebuilt static Console and runtime prompt/skill resources. Node.js is not
needed to run this wheel. The Docker sandbox image must be deployed separately.

Install your locally built wheel into a fresh environment with Python 3.12+:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install ./dist/strixops-1.3.5-py3-none-any.whl
.venv/bin/strixops --version
.venv/bin/strixops-console --runs-root "$PWD/strix_runs"
```

Provide a compatible Docker image separately and preserve the configured data
paths when replacing an existing deployment. See the [README](../README.md) for
requirements and [management guide](management.md) for service and data handling.
